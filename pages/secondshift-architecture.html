SecondShift

A C++23 backend foundation for a chat application. The implemented runtime covers HTTPS authentication, account lifecycle management, PostgreSQL persistence, and a reusable asynchronous HTTP server.

C++23Boost.Beast / AsioPostgreSQL 16OpenSSLDocker Compose development

Runtime topology

Client traffic enters the TLS listener. The authentication service routes requests to account or session logic; repositories use a bounded connection pool to access PostgreSQL.

Request and token flows

Account creation

POST /api/v1/auth/users

JSON validation → uniqueness checks → scrypt password hash → database insert. Response uses an explicit field allowlist.

Login

POST /api/v1/auth/login

Look up active account → verify scrypt hash → create session → persist refresh-token hash → return short-lived access JWT and opaque refresh token.

Access renewal

POST /api/v1/auth/refresh/access

Validate refresh token against stored hash and account state → issue a new access token. Refresh token lifetime is unchanged.

Refresh rotation

POST /api/v1/auth/refresh

Validate token → atomically replace its stored hash → return a new opaque refresh token with a fresh seven-day lifetime. The session ID stays the same; concurrent reuse allows at most one rotation.

Current account

GET /api/v1/auth/me

Verify JWT signature, issuer, audience, and time claims → check the session and account in PostgreSQL → return the active account’s login name and email.

Change password

PATCH /api/v1/auth/changemypwd

Require a valid Bearer token, current password, and matching new-password fields. Atomically update the password hash and revoke all sessions, including the current session. Log in again afterwards.

Delete own account

DELETE /api/v1/me

Require a valid Bearer token and current password. Atomically mark the account DELETED and revoke all sessions. Rows remain stored; login names and emails stay reserved.

Account lifecycle and revocation

Protected account actions share AuthController::authenticate_request(). Identity comes from the verified JWT subject; clients cannot choose a target account ID.

sequenceDiagram participant C as Client participant A as AuthController participant S as SessionManager participant M as AccountManager participant DB as PostgreSQL C->>A: PATCH password or DELETE account + Bearer JWT A->>S: verify_access_token(jwt) S->>S: Verify RS256 and required claims S->>DB: Check session ownership, expiry, revocation and account state DB-->>S: Eligible session and account S-->>A: Verified user ID A->>M: Change password or delete own account M->>M: Verify current password; validate new password if changing M->>DB: Begin transaction; lock eligible account and recheck password hash M->>DB: Update password hash OR mark account deleted M->>DB: Revoke all unrevoked sessions M->>DB: Commit M-->>A: Success A-->>C: 200, no-store; existing tokens rejected on subsequent checks

Password changes require current_pwd, new_pwd, and reenter_new_pwd; new passwords must exceed six bytes. Deletion requires current_pwd. Neither operation issues replacement tokens.

Components and responsibilities

HTTP library

Listener accepts TCP, TLS sessions parse requests and apply a 10 KiB body limit, Router matches method/path, SharedState owns routes. WebSocket session support exists in the shared transport layer.

Auth service

Main loads INI configuration and keys; Authentication initializes schema and starts the listener. Controller handles request/response validation. Managers hold account and token business logic. AccountManager coordinates password changes and soft deletion with session revocation in a single transaction.

PostgreSQL library

Connection pool owns fixed connections; move-only leases return connections on scope exit. Repository operations use pqxx transactions. TLS uses verify-full in the configured development setup.

Development environment

Compose runs a development app container and PostgreSQL. The app generates a CA and database certificate; the database receives only its server certificate and key. Build uses Conan and CMake.

Data model and security boundaries

erDiagram Users ||--o{ Sessions : owns Users { uuid id PK varchar login_name UK varchar normalized_login_name UK varchar email UK text password_hash varchar status timestamptz created_at timestamptz updated_at timestamptz deleted_at } Sessions { uuid session_id PK uuid user_id FK char token_hash UK timestamptz created_at timestamptz expires_at timestamptz revoked_at }
  • Passwords are stored as salted scrypt hashes; refresh tokens are random and only their SHA-256 hashes are stored.
  • Access tokens use RS256 with issuer SecondShift.Auth, audience SecondShift, subject user UUID, session ID, and 10-minute lifetime. Refresh tokens last seven days.
  • Refresh checks session expiry, revocation, and account active/deleted state. Protected account endpoints also verify the JWT’s sid belongs to its subject and references an unrevoked, unexpired session on an active account.
  • Database credentials and JWT private key paths come from service configuration/environment; development TLS CA and certificates are mounted as volumes.
Access-token verification queries PostgreSQL on each protected request. Committed session revocation causes subsequent checks to reject existing access tokens. Refresh-token rotation alone preserves the session and does not invalidate existing access tokens.

Configuration and deployment

Build

Conan dependencies feed CMake; CMake builds shared libraries and service executables under Server/.

Auth service configuration

AuthenticationService.ini sets bind address/port, worker threads, DB pool size and env file, log file, TLS certificate/key, and JWT key files. Relative paths resolve against the INI file directory.

Compose network

App reaches database as postgres:5432; host ports 8080 and 5432 are published. PostgreSQL data persists in a named volume.

Current scope and known gaps

Implemented

  • Seven authentication and account endpoints listed above
  • Password changes and account soft deletion with atomic session revocation
  • Database-backed access-token session checks
  • HTTP routing and TLS listener
  • Users/Sessions schema creation
  • Postgres pool and transaction wrappers
  • Example HTTP service

Not implemented or incomplete

  • Messaging, conversations, presence, and chat persistence services
  • Schema migration framework; current migrate() is a no-op
  • Standalone logout and session-management endpoints
  • Authorized password-reset and initial-password setup flows
  • Rate limiting and expanded password policy
  • Production secrets/certificate lifecycle and deployment configuration

This page describes the repository’s current implementation, not the aspirational requirements in the architecture diagrams. Development defaults are not production credentials.
